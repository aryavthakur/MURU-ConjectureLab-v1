## 4. Root causes

Two independent failure modes, diagnosed separately.

### 4a. Shard 2: unbounded sympy classification (the F09-class hang)

`src/muru/v2_calibration/e2_classify.py` already declared, in its own docstring, the exact mitigation this class of failure needs: *"memoise by expression string ... apply a per-expression wall-clock cap with the timeout recorded as an explicit SIMPLIFY_TIMEOUT status rather than silently becoming None."* It implemented that cap with `signal.alarm(5)` around only the `sympy.simplify()` call.

Live diagnosis (process still running, not yet killed) via macOS `sample` on PID 46829, two independent 3-second captures a minute apart: 2137/2137 and comparable sample counts, both entirely inside `_PyEval_EvalFrameDefault` -> `bounded_lru_cache_wrapper` (sympy's own `@cacheit`) -> `type_call`/`slot_tp_new`/`slot_tp_init` (sympy `Basic.__new__` object construction) -> `set_update`/`builtin_all`/`gen_iternext` (assumption/`free_symbols`-style set-building over a generator). No native/BLAS frames anywhere in either sample -- pure-Python the whole way down, and this venv has no `gmpy2` (`mpmath==1.3.0`, pure Python), so a C-extension swallowing the `SIGALRM` before it reaches the interpreter is not the mechanism. The process had produced zero output for 6.5+ hours against a largest-ever-observed legitimate single-world wall time of 7305s (~2h, shard 1's own log) -- three orders of magnitude past the declared 5s cap.

Reproduced directly: a synthetic `sympy.simplify` replacement that runs a `while` loop wrapped in `try/except Exception: continue` (mimicking sympy's own internal broad-except fallback strategies) defeats the original `_with_timeout`/SIGALRM guard completely -- the alarm fires once, is caught and discarded by the loop's own `except`, and the call never returns. This is a known, documented class of Python gotcha (a one-shot `SIGALRM`-raised exception can be caught and discarded by any `except Exception` between the raise point and the caller), not specific to this codebase.

Also found, while diagnosing: `sympy.simplify` was the *only* call in `classify_expression`'s pipeline under any timeout. `extract_effective_support`, `classify_discovered_family`, `parse_production_candidate`, `template_key`, `template_key_string`, and `coefficient_vector` -- all of which do further sympy manipulation on the same parsed expression -- ran completely unguarded. The live hang cannot be attributed with certainty to `sympy.simplify()` specifically rather than one of these; the stack signature is generic to sympy's object-construction/caching machinery, which all of these touch.

### 4b. Shard 0: silent process death, cause not fully forensically determined

No traceback anywhere (stdout capture is 0 bytes for the shard's entire life), no entry in an errors file (none was ever created for shard 0), and no macOS crash report (`~/Library/Logs/DiagnosticReports/`) in the relevant window -- consistent with an external `SIGKILL`-class termination (uncatchable, no traceback possible, no crash report generated) rather than an in-process exception or native fault. It died at the same point (immediately after the shard-assignment header, before completing world 1) on both of its two launches (once under `--n-shards 5`, once under `--n-shards 3`).

To test whether this is a reproducible code defect specific to shard 0's first-assigned world, that exact world (`mass_affine_descriptor|low|noiseless|r000`, ordinal 0) was re-run in complete isolation, in a scratch directory, under full stdout+stderr capture, using the unmodified frozen pipeline (`build_world` -> `run_seed_search` x30 -> `evaluate_world`). It progressed cleanly through at least 12 of 30 seeds (each logging normally) and then **also died silently**, with the identical signature: no traceback, no error, process simply gone. `log show` for the relevant window turned up no jetsam/memorystatus kill record either (though this may reflect log retention/redaction rather than absence of such an event; root cause is not claimed to be fully proven).

**Conclusion:** shard 0's death is not attributable to a reproducible logic defect in the per-world computation pipeline -- the same pipeline, run in isolation, completed 12+ seeds of identical work twice before also dying with the same untraceable signature. It is treated as an external-kill-class failure requiring supervision (retry-on-death), not a code fix.

## 5. Rescue diff

Both changes live entirely outside the manifest's 17 frozen scientific files. Blob hashes of all 17 re-verified unchanged after the diff (see `04_hash_verify.txt` vs. a post-diff re-run).

### 5a. `src/muru/v2_calibration/e2_classify.py`

The pre-declared cap (`SIMPLIFY_TIMEOUT_SECONDS = 5`, unchanged) and the pre-declared status name it reports on a cap-out (`SIMPLIFY_TIMEOUT`, unchanged) are now enforced at a process boundary instead of an in-process signal:

- The full per-expression computation (parse through `coefficient_vector`, i.e. everything `classify_expression` used to do directly) is unchanged in content, only relocated verbatim into `_classify_compute`.
- A single **persistent** forked worker process (`_get_worker`/`_worker_loop`) services every `classify_expression` call for the life of the shard process, exactly as the original single in-process design did -- this specifically preserves sympy's own internal `@cacheit` memoization warming up across thousands of calls over a shard's lifetime, which a first (rejected) fork-per-call design discarded, manufacturing new near-boundary timeouts that do not occur in the original code (caught by a before/after parity check, see \S6).
- The parent enforces the cap with `conn.poll(SIMPLIFY_TIMEOUT_SECONDS)` and, on timeout, `Process.kill()` (`SIGKILL`) -- unlike `SIGALRM`, this cannot be caught, delayed, or discarded by any exception handler anywhere in the call graph, including inside sympy's own internals. On a genuine timeout the (possibly wedged) worker is killed outright and a fresh one is lazily spawned on the next call; the pre-declared `SIMPLIFY_TIMEOUT` fallback record is returned, field-for-field identical in shape to the one the original code already produced for this status.
- `template_key_value` (a tuple that can hold live, deeply-nested sympy objects for pathological candidates) is never marshalled back across the worker's pipe. This field is verified dead for E2's purposes by exhaustive grep across `e2_search.py`, `e2_scoring.py`, `e2_aggregate.py`, `rc5_selection.py`, `scripts/`, and `tests/`: nothing reads `classification.template_key_value`. `FrontRow` only ever carries `template_key_repr` (the string form, sent in full, unchanged). The actual scientific consumer of template keys -- `rc5_selection.py`'s cross-seed equivalence classing (frozen, untouched) -- independently recomputes `template_key(parse_production_candidate(...))` directly from the raw expression string; it never reads anything `classify_expression` returns for this field. Pickling a large sympy tree turned out to re-trigger close to the same expensive object-construction machinery paid to build it in the first place, which was itself large enough to manufacture false timeouts on IPC cost alone for a small number of pathological-shaped candidates -- stripping this genuinely-unread field removes that cost with no observable effect anywhere in the pipeline.

Net effect for every expression whose true classification cost stays within `_classify_compute`'s own wall time (the overwhelming majority): identical output to the original code, memoization-warm performance included. For an expression that hangs anywhere in the pipeline (not just inside `sympy.simplify`): guaranteed termination at 5s instead of an unbounded hang. See \S6 for the one identified category of narrow, deliberate, and here-verified-inert exception to "identical output."

### 5b. `scripts/e2_run_shard.py`

One additive, backward-compatible CLI option: `--only-worlds-file PATH`, taking a JSON list of world IDs. When given, `run_shard` restricts its normal shard assignment to the intersection with that list; when omitted (the default, used by every non-rescue invocation), behavior is byte-identical to before. Used only to drive the replay gate (\S6) and the targeted single-world verification in \S6 -- never to change which worlds a production shard run computes.

### 5c. `scripts/e2_shard_supervisor.sh` (new)

A restart-on-death wrapper around `e2_run_shard.py`. It launches the shard, and if the process exits without a `shard N COMPLETE` marker in its log, restarts it (up to `--max-restarts`, default 20), relying entirely on `run_shard`'s own unmodified `_already_done()` checkpoint to resume rather than repeat completed worlds. It adds no new computation and makes no decision about world content, ordering, or classification -- it only notices a shard process is gone and tries again. This is the mitigation for \S4b (shard 0's untraceable external-kill-class death): whatever kills a shard process externally, a restarted shard resumes from its own persisted checkpoint.

## 6. Why this is computational, not scientific

- None of the 17 frozen-hash scientific files change (byte-identical blobs, re-verified post-diff).
- No classification, equivalence, canonicalization, retention, aggregation, family-classifier, grammar, seed, world-definition, partition, or threshold *semantics* change. `SIMPLIFY_TIMEOUT_SECONDS` keeps its pre-declared value (5); `SIMPLIFY_TIMEOUT` keeps its pre-declared meaning and is still produced by exactly the same triggering condition family (a per-expression cost cap being exceeded) -- only *where* (process boundary, not signal) and *how completely* (the whole pipeline, not just one call inside it) that pre-existing, pre-declared cap is enforced.
- `_classify_compute`'s own body is a verbatim relocation of the original `classify_expression` computation; nothing about *how* an expression is classified changed, only *where* that computation runs and how its result crosses back to the caller.
- The one identified, non-trivial behavioral difference -- documented in full below rather than glossed over -- is that the original cap only ever bounded the `sympy.simplify()` sub-call, never the full pipeline (`extract_effective_support`, `classify_discovered_family`, `template_key`, `coefficient_vector` were always unguarded). Closing that coverage gap is *necessary* to actually guarantee termination against a hang located anywhere in the pipeline (the live shard-2 hang's exact location within the pipeline was not pinned down with certainty -- see \S4a) but it does mean an expression whose `sympy.simplify()` sub-call finishes under 5s while its *total* classification cost exceeds 5s will now correctly report `SIMPLIFY_TIMEOUT`, where the original's incomplete coverage let it run unbounded and eventually report `OK`. This was caught empirically (\S7) rather than reasoned about only in the abstract, and is reported honestly against the replay gate below rather than argued around it.

### 7a. What was run

Before committing to the expensive full production replay (re-running all 30 PySR searches per world for all 37 worlds), a cheaper, decisive pre-check was run first: for every one of the 37 completed worlds, extract its front-candidate expression strings in true first-appearance order (exactly the order the real shard process encountered them) and classify each one under (a) the original pre-rescue `e2_classify.py` and (b) the rescued one, each in its own fresh process (mirroring a shard's cold start), then diff every `canonicalization_status`.

One full production single-world replay was also run end-to-end (`mass_affine_descriptor|low|noiseless|r010`, via `e2_run_shard.py --only-worlds-file`) and diffed field-for-field against the preserved original candidate rows and world-outcome row, to confirm the classify-layer check's finding actually propagates to persisted, scientifically-relevant output (it does: `n_seeds_correct_on_front` 19->18, `n_seeds_retained_correct` 9->8, and multiple candidate rows flip `support_status_vs_truth`/`family_status_vs_truth`/`g2_event`, not just internal classify-layer bookkeeping).

### 7b. A load-contention confound, isolated and controlled for

This host was, for much of the diagnosis window, extremely oversubscribed by unrelated concurrent processes (other sessions on the same shared machine -- confirmed via `ps aux`: unrelated `miniconda3`-based `multiprocessing.spawn` workers and an unrelated `pytest` run, neither started by this rescue). Load average peaked at 220 on an 8-core host. Under that load, the *first* single-world replay attempt showed cascading `SIMPLIFY_TIMEOUT`s even for trivially simple candidates (e.g. `x1 + 0.5505815`), which reproduced as `OK` in isolation and did not recur once load dropped -- consistent with OS scheduling starvation of the forked worker rather than a mechanism defect. This was verified directly: the same 272-expression true-order sequence for that world, re-run once load fell to a comparable range for both the original and rescued code, dropped from cascading failures to a small, stable, non-load-sensitive set. **The load-contention effect is real and was isolated and excluded from the finding below** -- what remains, checked under calm conditions with load consistently under ~20 on an 8-core host, is not attributable to it.

### 7c. The confirmed, reproducible finding

31 of 37 worlds checked at the classify layer under calm conditions (the remaining 6 were still checking when this section was written; see the live log for the final count -- the verdict below does not depend on them, since the gate already fails at 31/37):

- **24 worlds: 0 status flips.**
- **7 worlds: 12 total status flips, all `OK -> SIMPLIFY_TIMEOUT`, every one of them a heavily/multiply-nested candidate** (e.g. `cube(inv(square(square((91.283775 / (x1 + x0)) - -1.104039))) + 0.79000676)`, `square(square(square(square(cube(((x1 * -0.012647588) - 0.99806005) + inv(x0))))))`, `sqrt(sqrt(cube(sqrt(cube(cube(log(log(sqrt(x0))) - 0.06393476)) + square(x1)))))` -- see the full log for all 12).

Mechanistically understood, not just observed: the *original* code's `signal.alarm`-based cap only ever bounded the `sympy.simplify()` sub-call (\S4a) -- `extract_effective_support`, `classify_discovered_family`, `template_key`, `template_key_string`, and `coefficient_vector` ran completely unguarded, so an expression whose `simplify()` call finished under 5s but whose *total* classification cost ran over could complete unbounded and eventually report `OK`. The rescue's process-boundary cap necessarily bounds the *whole* `_classify_compute` pipeline -- bounding only `simplify()`, matching the original's exact (incomplete) scope, was considered and rejected: the live shard-2 hang's stack signature (\S4a) was generic to sympy's object-construction/caching machinery used throughout the pipeline, not proven to sit specifically inside `simplify()`, so narrowing the guard back to the original's scope would risk reopening the exact vulnerability this rescue exists to close.

This is a real, reproducible, understood difference in output for specific pathological-shaped candidates -- not an artifact, not noise, and not something to argue around. It is exactly the class of thing this hard gate exists to catch.

## 9. Two more issues found live during the restart, both fixed in-flight

### 9a. Shard 0's exact original symptom recurred -- and turned out to be a real external SIGKILL

Once the fresh restart was running, shard 0 (and only shard 0) began dying repeatedly under the supervisor -- `git log`-visible as commit `bc30b12`'s and this section's context. Every exit code was **137 (128 + SIGKILL)**, confirmed via `ps`/exit-code inspection, not inferred: this is conclusive, not circumstantial -- a Python process cannot SIGKILL itself by accident, so this is definitively an external kill, matching \S4b's diagnosis of the original death exactly (same world, same signature, same shard index). `PhysMem` on this host was reading ~14G/16G used at the time (unrelated concurrent sessions, per \S7b), consistent with an OS-level low-memory kill of a background process, though this remains the same not-100%-provable-by-log-alone conclusion as \S4b. The supervisor did exactly its job -- caught every death, restarted from checkpoint (world 1 was never reached, so nothing to resume past) -- but was burning through its 30-attempt budget on a ~4-6 minute cadence. Mitigation: relaunched shard 0's supervisor with `--max-restarts 500` (cheap per attempt, no scientific effect, purely absorbs however many external kills it takes).

### 9b. Found and fixed live: killed shard-0 attempts were leaking their classify worker as an orphan

Between shard 0's repeated kills, `ps` showed the classify worker child accumulating as an **orphaned, indefinitely-alive process** instead of exiting -- 15 of them within about 70 minutes, each blocked forever on `conn.recv()` at ~0% CPU. Root cause: `fork()` duplicates the whole file-descriptor table, so the child also held its own unclosed copy of the *parent's* end of the duplex pipe; a socketpair only signals EOF once every reference to the peer's end -- including the child's own redundant one -- is closed. When the true parent was SIGKILLed, the orphaned child never saw that as EOF (it still held a live reference to the peer side itself) and blocked forever instead of exiting. Fixed in commit `bc30b12`: the worker now explicitly closes its inherited copy of `parent_conn` immediately on start. Verified directly (not just reasoned about): a throwaway "fake parent" process was spawned, made to start a worker, then `SIGKILL`ed -- before the fix this leaves the worker running; after the fix, `ps` confirms the worker is also gone within seconds, every time. This bug did not cause \S9a's kills (it postdates them) but was compounding resource pressure on top of them and is exactly the kind of thing this rescue's own supervision was supposed to prevent, not add.

### 9c. Found live: the shard-death supervisor doesn't cover a shard that's alive but not progressing

While investigating 9a, shard 2 (not shard 0) went 65+ minutes without a new completed-world log line, prompting a live re-check of its stack (`sample`, same method as \S4a) -- inconclusive on its own (still inside sympy's `bounded_lru_cache_wrapper`/`type_call` machinery, indistinguishable at this resolution from legitimately slow real work; shard 1 independently proved a single world can legitimately take 46 minutes around the same time). This exposed a real design gap rather than resolving the specific question: `e2_shard_supervisor.sh` only reacts to a shard process *dying* -- it does nothing if a shard stays alive while stuck, which is exactly what the original shard 2 did for 6.5+ hours (\S4a) before this rescue even started. Closed with a new, additive, computation-free script, `scripts/e2_staleness_watchdog.sh` (commit `5da8ace`): polls each shard's log-file mtime every 5 minutes, and `SIGKILL`s a shard's process if its log has gone stale for more than 3 hours (roughly 1.5x the largest legitimately-observed single-world wall time anywhere in this run's own logs, ~7305s/122min) -- the existing supervisor then sees an ordinary death and restarts from checkpoint, no different from any other kill.

### 10b. PySR/seed parallelism structure

`SEARCH_SETTINGS["procs"] = 0` in `calibration_contract.py` (frozen, on the manifest's hash list) is explicit and deliberate -- PySR/SymbolicRegression.jl runs each seed's search as a single serial process, coupled to `"deterministic": True`. This is not available to change (it is exactly the kind of search-budget/determinism setting this rescue is barred from touching), and is not why the run was slow.

What it does mean: each of a world's 30 seeds is already, by design, a fully independent, single-process, single-seed unit -- nothing about the frozen config requires them to run in the same OS process, only that each individual seed's own search stays serial internally. **World-level concurrency (more shard processes, each running the exact unmodified `e2_run_shard.py`, on disjoint world subsets) exercises exactly this independence and touches no frozen setting at all.** Seed-level concurrency (splitting one world's 30 seeds across processes and reassembling in seed-ordinal order before aggregation) was assessed as theoretically viable on the same grounds but was **not implemented or benchmarked** -- world-level concurrency alone was sufficient (\S10d), and seed-level parallelism would need its own from-scratch parity proof per this investigation's own rule, which was not worth the added complexity/risk given the simpler lever already worked.

### 10c. Two more execution-only bugs found and fixed live

Both found by the benchmark harness itself, both fixed before trusting any benchmark number, both computational/orchestration-only:

1. **`e2_shard_supervisor.sh`'s empty-array expansion.** `"${EXTRA_ARGS[@]}"` on a genuinely empty array is an unbound-variable error under `set -u` on bash 3.2 (macOS's default `/bin/bash`, still bash 3.2 for licensing reasons). Guarded with a length check before expanding. (Caught immediately on first launch of this section's benchmark harness; trivial, included for a complete record.)

2. **A shard process that finishes all its assigned worlds cleanly never actually exits.** Found when a serial (concurrency=1) benchmark run sat idle at 0% CPU for 7+ minutes after its log already showed `shard 0 COMPLETE`. Confirmed via `sample` (the same tool used throughout this rescue): the process was permanently blocked in `_Py_Finalize -> atexit_callfuncs -> os_waitpid`. Root cause: `multiprocessing`'s own atexit cleanup sends the daemon classify-worker SIGTERM, then does an untimed `os.waitpid()` on it; the worker forks *after* this process has already loaded PySR/Julia (`e2_search` is imported above `e2_classify` in `e2_run_shard.py`), and something in that inherited Julia runtime state intercepts or delays plain SIGTERM, so the worker never dies from it and the parent hangs forever. SIGKILL (this module's existing `_kill_worker`) always reaps it immediately.
   - First fix attempted (commit `02fdbb4`): register `_kill_worker` with `atexit`, on the theory that atexit runs LIFO and a module-level registration in `e2_classify.py` would therefore fire before `multiprocessing`'s own handler. **Verified live that this did not work** -- `multiprocessing` registers its cleanup at first `Process` creation, not at `import multiprocessing`, so it ends up registered *after* this call and still runs first, blocking before the atexit-registered fix ever gets a turn.
   - Actual fix (commit `7925e5b`): a new public `e2_classify.shutdown()`, called explicitly in a `finally` block at the end of `run_shard()`. This runs deterministically before the interpreter's own shutdown sequence begins at all, independent of atexit ordering. Verified directly: a single-world run that previously hung indefinitely now exits with code 0 within ~1 second of finishing its last world, and produces output byte-for-byte identical (excluding `wall_seconds`) to the pre-existing reference for that world.
   - Both this and \S9b's orphan-leak fix are the same general class of defect (this rescue's own worker-lifecycle plumbing, not the frozen scientific pipeline) surfacing under conditions the earlier, lower-throughput 3-shard run had not exercised or had not run long enough to expose.

### 10d. Benchmark: concurrency 1/2/3/4, fixed 4-world set, scratch directories

Four already-completed worlds of similar historical cost (~118-168s each) were re-run from scratch (not resumed) at each concurrency level, each concurrent worker as an unmodified `e2_run_shard.py --shard-index 0 --n-shards 1 --only-worlds-file <its-own-world-subset>` process in its own scratch subdirectory (no shared output files, no write races possible). Every worker uses the exact production code, same commit, same config.

Concurrency=3 underperforming concurrency=2 is a small-sample artifact of this specific 4-world set splitting unevenly across 3 workers (2+1+1, bottlenecked by the pair) -- not a defect in the mechanism, and not expected to recur at production scale where each shard gets dozens of worlds and the existing interleaved `world_ordinal % n_shards` assignment (already designed, per its own docstring, to spread hard/slow cells evenly rather than concentrate them) evens this out much better than 4 hand-picked worlds can.

**Parity: every world, at every concurrency level, matched the authoritative pre-stop reference exactly** -- full world-outcome row and every candidate row, all fields except the explicitly-allowed `wall_seconds`. Process inspection during the concurrency=4 run: each worker used 117-165% CPU (i.e. more than one core each -- `cap_threads()` pins the numeric-library thread env vars but does not touch Julia's own internal threading), summing to ~582% across 4 processes on an 8-core host. This directly bears on the "4 or more only if...sufficiently single-threaded and capacity available" condition: units are not strictly single-threaded, so headroom past 4 is real but not unlimited.

### 10e. Dynamic scheduling: evaluated, not implemented

Static equal-count sharding (`world_ordinal % n_shards`) is already interleaved by design specifically to avoid concentrating hard/slow cells in one shard (\S file docstring, unchanged). The only long-tail imbalance actually observed in this investigation (concurrency=3's 2+1+1 split) is an artifact of testing with 4 hand-picked worlds, not of the real ~86-worlds-per-shard production split. Implementing a genuinely safe dynamic disjoint-world work-queue (atomic claim, exactly-once execution, no output races) is real additional complexity for a benefit that the existing interleaved static assignment already substantially captures. Given the explicit "prefer dynamic scheduling *if* scientifically equivalent" is conditional, not mandatory, and given the goal is fastest *safe* completion rather than a theoretically optimal schedule: **not implemented.** Static sharding, just with more shards, is the selected lever.

### 10f. Configuration selected

**6 static shards** (up from 3), same `e2_run_shard.py`, same `world_ordinal % n_shards` assignment, each under `e2_shard_supervisor.sh` (restart-on-death) and the staleness watchdog (restart-on-stuck), exactly as before -- only `--n-shards` changes, from 3 to 6. Rationale: measured 1->2 shard speedup (1.73x) is well short of oversubscription; measured per-worker CPU (117-165%) means 6 shards is a conservative estimate of ~7-8 of 8 cores, leaving headroom rather than exceeding it; going straight to 8 was rejected given units are not strictly single-threaded and this host is shared. No world's assignment, seed derivation, or computation changes -- only how many shard processes divide the same 540-world, `world_ordinal`-keyed population.

Before resuming, the pre-existing manifest and completed-world set were re-verified consistent with the resume plan: 23/540 completed (0/1/20/3... i.e. 0+20+3), all preserved and none invalidated by anything in this section -- concurrency was proven scientifically inert, so there is no basis to discard them. Resume proceeds by launching 6 supervised shards (`--n-shards 6`, `--shard-index 0..5`) plus the staleness watchdog against the same `results/e2/run/` directory; each shard's own `_already_done()` checkpoint means the 23 already-persisted worlds are skipped automatically, not recomputed.

## 11. Found live during the 6-shard resume: staleness watchdog only covered 3 of 6 shards

At 170/540 (~6h into the 6-shard resume), a slowing completion rate prompted a direct per-shard health check rather than assuming the aggregate progress number told the whole story. Found: shard 5 had been alive and burning ~88% CPU with **zero log progress for 6+ hours** (more than double the 3-hour staleness threshold), and shards 3 and 4 were also past threshold (190min and 185min). Root cause: `e2_staleness_watchdog.sh`'s `for i in 0 1 2` loop was written for the original 3-shard design and never updated when \S10f moved production to 6 shards -- shard indices 3, 4, 5 were simply never in the loop, so the watchdog silently covered half the actual shards. All three stuck processes were killed manually the moment this was found; their supervisors picked them up from checkpoint immediately. Fixed the watchdog itself to discover shard indices by globbing `log_shard_*.txt` rather than a hardcoded range, so this class of silent under-coverage can't recur regardless of shard count (commit follows this entry).

## 12. Shard 0's external-kill pattern persisted through the 6-shard resume

Shard 0 (world_ordinal 0's bucket, same shard index implicated throughout \S4b, \S9a) failed 71 consecutive attempts over ~7.5 hours in the 6-shard resume -- 0 worlds ever completed -- every exit code 137 (SIGKILL), at a strikingly regular ~6-6.5 minute cadence. All other 5 shards progressed normally over the same window (shard 2 completed its full 90-world allocation cleanly). Supervisor budget (500 attempts) was not close to exhausted, so no worlds were lost, but this remains an open, unresolved, environment-level issue -- not a code defect (identical code runs cleanly on every other shard). The supervisor's own bash process (alive continuously since the original 6-shard launch, having restarted its child 71 times) was killed and relaunched fresh as a low-cost experiment to see whether the *supervisor's* own long-lived state was a factor; result pending at time of writing.

## 13. Shard 0 isolated: routed around the one perpetually-killed world

Shard 0's fresh-supervisor experiment (\S12) did not help -- 5 more consecutive SIGKILLs at the same ~6-6.5min cadence, 76+ total attempts, 0 worlds ever completed. Since `_already_done()` always finds shard 0's world list empty, every attempt necessarily restarts from the exact same first (deterministic-order) world every time: `V2C|E2|mass_affine_descriptor|c_low|n_noiseless|r000` (world_ordinal 0) -- the same world implicated throughout this rescue (\S4b's isolated re-run, the original shard 0 death). The strikingly consistent kill cadence across dozens of independent attempts is far more consistent with something about *this world's own computation* (most likely progressive memory growth crossing a host memory-pressure threshold at a repeatable point) than with generic external noise, though the exact trigger remains unconfirmed (no root/sudo access to inspect the OS-level kill decision further).

Routed around it rather than continuing to retry blindly: shard 0's other 89 worlds were relaunched under `--n-shards 1 --only-worlds-file <the 89, minus the one>` against the same `results/e2/run/` directory (an additive restriction, not a scientific one -- see \S5b), so they can progress immediately. The one poison world was given its own isolated, unlimited-patience supervisor (`--max-restarts 2000`) writing to a **separate** scratch directory, `results/e2/run_poison_world/`, specifically so its repeated failures cannot block or interleave with anything else. (One own mistake caught immediately: the first attempt at this used `--shard-index 6 --n-shards 1` for the poison-only supervisor, which hits the exact same `ordinal % n_shards` bug documented in \S10d's benchmark harness -- `world_ordinal 0 % 1` is never `6`, so it silently "completed" with 0 worlds attempted. Fixed by using `--shard-index 0 --n-shards 1` (the only combination that passes the modulo filter unconditionally) with a distinct output directory instead of a distinct shard index.)

If/when the poison world eventually succeeds in its isolated directory, its single `worlds_shard_000.jsonl`/`candidates_shard_000.jsonl` record will be merged into `results/e2/run/` by appending (verified by world_id uniqueness against the rest of the population) before the final 540/540 completeness check -- not before.

## 15. Four more worlds found stuck in a deterministic 3-hour retry loop; isolated and quarantined

At 216/540, the rolling report showed shards 1, 3, 4, and 5 with zero completions across a full hour despite a ~230s median world runtime. Direct investigation found this was the staleness watchdog itself repeatedly catching and restarting all four shards at almost exactly the 3-hour threshold (not new external SIGKILLs) -- but because `_already_done()` never marks an unfinished world done, every restart necessarily re-attempts the exact same first-in-queue world, so each shard was looping: run 3 hours, get killed, restart, run the same 3 hours on the same world, get killed again -- never reaching its other 89 worlds. This is the same structural failure as the original poison world (\S13), on a much longer cycle.

Live `sample` inspection of shard 1's stuck process (two captures 20s apart) distinguished this from a frozen no-op: a deep, evolving stack of sympy `type_call`/`slot_tp_new`/`slot_tp_richcompare`/`tuplecontains` recursion, and a peak physical footprint of 1.8G against a 990M current -- real, if expensive, computation, not literally nothing happening. Whether it is genuinely unbounded or merely very slow was not established either way -- none were left running past 3 hours on the production host to find out, per the same "stop before it materially consumes further resources" threshold already applied to the original poison world.

Identified world_ids (one per shard, each the deterministic first-in-order not-yet-done world at time of intervention): `mass_power|c_low|n_strong|r007` (shard 1), `mass_power|c_high|n_default|r003` (shard 3), `mass_saturating_descriptor|c_mid|n_strong|r010` (shard 4), `mass_affine_descriptor|c_low|n_noiseless|r011` (shard 5). Each shard's supervisor+process was stopped and relaunched restricted to its other 89 worlds (`--only-worlds-file`), each in its **own isolated output directory** (`results/e2/run_shard{1,3,4,5}_healthy/`) rather than the shared `results/e2/run/` -- multiple `--shard-index 0 --n-shards 1` processes (the only combination that passes the ordinal-modulo pre-filter for an arbitrary world subset; see \S13's own note on this exact gotcha) writing to the same filename would otherwise race. These will be merged into `results/e2/run/` once complete, checked for world_id uniqueness first. No further retries of the 4 newly-stuck worlds were started on the production host; full record (including the two `sample` captures) in `results/e2/run_stuck_worlds/PENDING_EXECUTION_DIAGNOSIS.md`, read-only.
